# Claude adapter preview (M3)

The installed adapter accepts **Claude Code >=2.1.306**, without an upper bound.
Newer versions have full existing capabilities with `newer_unverified`; ask stays
separately qualified and verified-only. See the [runtime policy](spec/versions.md).
The original
[lab evidence](../research/lab/results/m3-claude/README.md) covers Linux ARM64
with the DeepSeek gateway on 2.1.306; it does not qualify newer runtime semantics.
**0.1.4-preview is prepared, not yet published.** Its [installer pins](install.md)
become usable once signed assets and attestations exist. The candidate fixes
v0.1.2-preview's historical hooks-loader rejection using literal native API calls
and adds model-free cold MCP recovery plus [Claude-only connect](connect.md).
The [macOS live7 summary](../research/lab/results/macos-live-7/README.md) retains
its original pinned checks and limits.

Earlier source CI and maintainer-reported Claude 2.1.308 functional checks
covered fresh nonadmin link creation, current MCP, reuse and 25 seconds idle.
A first-warning ordering deviation prevents a complete procedural pass.
This candidate's gates, signed install, Haiku, two-host, owner-pasted join and
model reply acceptance for `.4` remain pending. These checks do not extend the
packaged verified list.
The original M3 responder limits below are separate from the later, narrow
[M6 Linux qualification](m6-ask.md).

The adapter implements exact current-session binding, live coauthor delivery and
no-wake inform notices with explicit inbox reads. **M3 is not fully accepted:** automatic ask remains closed
with `protected_path_policy_failed`, `fork_responder=false` and
`authority_secrets_isolated=false`. The Go restricted runner and redactor exist,
but a qualified authority/snapshot/model profile and automatic signed ask-answer
pipeline are still required. A separate native fork experiment is not proof of
product ask support. No failure falls back to live delivery.

## Installation and operation

Build with the pinned Makefile, then install the local marketplace/plugin using
the target runtime's plugin commands. Configure the plugin's `peerturn_binary`
option to the absolute executable path. The plugin is at `adapters/claude` and the
marketplace is `.claude-plugin/marketplace.json`. See the
[plugin contract](../adapters/claude/README.md) and target-runtime lab commands.
Plugin installation alone does not prove activation; reload/resume may be needed.

After normal native approvals/activation, `peerturn connect --relay
https://relay.example` in the selected Claude session's own tool child prepares
its profile/daemon, proves one binding and returns one link. Use `--no-invite`
for receiving readiness. Explain coauthor strong trust before initialization
or access. Default closed relays require operator authorization; only an
operator can enable self-service. Neither path changes remote policy implicitly.
An uncertain bind remains `in_doubt`; do not submit another challenge blindly.

MCP discovery may precede the daemon or binding. After first binding, retry
`peer_status` on the same cold connection. Recovery submits no model prompt;
an already pinned epoch refuses a replacement and needs explicit reconnect.

Initialize one explicit local identity and start the private daemon as described
in [M2.5](m25.md). The mod inherits the same private runtime environment as the
daemon, including `XDG_RUNTIME_DIR` where the OS does not supply a usable private
temporary directory. It starts the Go helper through framed stdout and uses a
per-instance capability for loopback polling and acknowledgments.

Run current-session commands from the receiving session's own Bash child:

```sh
peerturn session bind --current
peerturn invite create --current --scope coauthor --json
peerturn join --link-stdin --current --scope coauthor --json < private-link-file
peerturn peers --current --json
printf '%s' 'literal message' | peerturn send --current --peer PEER --kind coauthor --stdin
printf '%s' 'stored notice' | peerturn send --current --peer PEER --kind inform --stdin
peerturn inbox --current --json
peerturn status --current --json
peerturn delivery resolve MESSAGE_ID --sent
peerturn delivery resolve MESSAGE_ID --not-sent
peerturn session unbind
```

The invitation remains a directional **coauthor** invitation. Its grant also
allows narrower inform/ask message kinds; this preview does not issue ask-only or
inform-only invitations. Ask kinds are rejected by the receiver preflight.
The pasted invitation fragment is visible to the agent's provider/transcript.
Never put the invitation or native token in argv or captured evidence.

In a Claude tool child, explicit `session bind --current` performs the native
nonce handshake. Other `--current` commands and MCP startup require an already
confirmed binding and read-only exact socket/process-ancestry/epoch proof,
including when an explicit preview label is also supplied. They never inject
a bind challenge. `invite create` requires `--current`.
Conflicting Claude and Codex current-session environments fail with `binding_mismatch`.
Explicit label-only transport commands remain available for M2.5 fixtures.
Cwd and display names are never selectors. The helper verifies the native socket's
kernel peer UID/PID and process start against its direct Claude parent, and checks
the socket inode throughout its lifetime. Explicit bind retains the nonce round
trip; read-only current resolution requires that exact host process as an ancestor.
Each daemon identity can bind one native UUID; a second UUID is rejected, even
in the same cwd. Concurrent sessions need separate isolated identity/runtime
environments. A reload/resume requires fresh continuity proof; no new UUID
inherits existing grants. `session unbind` clears the native binding, invalidates
all installed grants, cancels outstanding onboarding and releases MCP capabilities.
A subsequent session requires new grants. This is narrower than a multi-session
daemon registry. These owner commands use private same-UID IPC; reconciliation
and unbind are unavailable through MCP tools or peer ingress.

## Delivery and receipts

Coauthor text is locally framed with verified sender, scope and message ID,
JSON-escaped, with visible Unicode control/format/private-use/tag escapes, and
submitted with plugin provenance. It has the live agent's
normal capabilities: **strong trust, not a sandbox**. Peer text can influence
later owner turns. Permission mode, model, effort and tools are unchanged.

The mod holds work outside the native queue while the owner is busy or the
initial state is unknown. Main-turn completion establishes idle. It rechecks the
grant immediately before submit and respects native Esc/drop without replay.
Claude has no atomic conditional-submit API: a new owner turn racing the final
call can still cause native queue admission. Revocation cannot remove an already
admitted native item or undo effects. A lost native result becomes `in_doubt`;
the durable fence stops new live admissions across helper replacement/restart
until trusted native reconciliation. `delivery resolve MESSAGE_ID --sent` records
the owner's assertion that the exact ambiguous attempt was submitted;
`--not-sent` makes it eligible for a fresh attempt without claiming an effect.
Neither flag is an inference from a missing transcript item or a shell exit code.
The command rejects non-ambiguous attempts and never reverses revocation.

The store persists `authorized` immediately before submit. When a busy/session
check backs off before calling submit, the mod releases authorization. On session
exit/reload/helper restart, a never-authorized reservation closes as `not_sent`
and remains eligible; only authorized calls become `in_doubt`. Legacy intents
created by the earlier non-persisting implementation lack proof and conservatively
remain `in_doubt` for owner reconciliation. No database schema change is needed.
Per-item authority/framing failures receive their own rejected outcome and do not
block other peers. Transient IPC/poll errors back off without closing the binding;
replaced helpers exit, and idle helpers stop after 30 seconds without authenticated
requests. Unknown submit outcomes are never automatically resubmitted.
An authenticated native revoke closes sender admission even when its effect
outcome is `in_doubt/already_admitted`. If an unrelated terminal `in_doubt` was
already stored for that message, a later revoke receipt can still be suppressed
by receipt precedence; sender projection may remain stale. Receiver admission
remains revoked. That ordering case is not qualified by this preview.

Signed encrypted reverse-channel receipts distinguish receiver storage from
`adapter_accepted`, rejection and `in_doubt`. Native acceptance does not prove
model input, completion or reply. Sender visibility follows the daemon's normal
outbox synchronization, not the local IPC response time.
There is a crash window between committing local native-stage evidence and
journaling its reverse-channel receipt. A sender may retain `receiver_stored`
after such a crash; stage propagation recovery is not implemented here.

The owner decided after review to make inform notice-only, uniformly with Codex.
Inform is counted in status/UI without prompt submission. Only a host-stamped
`composer` or `bridge` prompt receives a small fixed-format notice: count,
verified sender labels and an instruction to use `peer_inbox` / `peerturn inbox`.
No peer body enters any prompt hook. The mod uses
`prompt.submit.context`; the classic `UserPromptSubmit` command deliberately
emits an empty object because its stdin does not establish human origin. This
differs from the originally requested classic `additionalContext` transport.
SDK, peer, plugin and slash-command prompts do not consume notices. The helper
receives no owner prompt text. Each notice covers at most 20 messages and is
bounded to 4096 bytes. The helper wait is capped at one second so a failure does
not block owner work. A notice reservation changes no durable delivery state;
`offered` / `hook_notice` is recorded only after the host accepts the
prompt carrying it. Unconfirmed/late reservations remain pending. Offered bodies
remain in the inbox. `delivered` / `inbox_body_returned` is acknowledged only after
the CLI or MCP proxy successfully writes the body response. This is tool-output
evidence, not proof of sampling, completion or reply. A crash between output and
its acknowledgment can leave a body eligible for another read.

## Ask runner boundary

The dormant Go runner fixes argv, stdin, private settings, tool inventory,
disabled hooks/plugins/MCP, environment allowlist, deadline, output cap and
concurrency. It validates a whole final JSON result and redacts deterministic
secret patterns. Deny rules use the documented filesystem-root form
`Read(//absolute/path/**)`, including protected PeerTurn state, credentials,
`.env*`, runtime metadata and process inspection paths. Rules alone do not prove
Grep/Glob, symlink, env, process, IPC or inherited-history isolation.

Without the complete local `AuthorityCheck`, it never spawns. Production CLI
operation does not expose a switch to bypass that gate. Full context/model/effort
continuity, committed busy snapshots, budget accounting, authority isolation and
the end-to-end signed answer path are outstanding acceptance work.

resolve protected roots from the actual macOS/XDG/custom daemon state, config and
runtime directories; require scoped read allowlists and test every OS layout;
qualify mod disabling with empty setting sources, `mcp__*` syntax, inherited
cross-peer history confidentiality and redaction of PeerTurn authority values.
The current dormant responder profile does not establish these properties.

the checksum manifest and archive, and excludes tests from the plugin payload.

OIDC release qualification remains separate from local key-signed lab evidence.
