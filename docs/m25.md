# M2.5: installed client preview

M2.5 connects two explicitly selected **test sessions** through the encrypted
relay. It implements local initialization, a foreground daemon, invitation/join,
encrypted message custody, CLI inspection and a seven-tool stdio MCP proxy.
Native Claude/Codex session binding, agent adapters, idle wake, turn-boundary
delivery and fork responders remain M3/M4 work. A test label is not evidence that
an agent received text. `inform` and `ask` remain disabled.

Only `coauthor` is available. It represents strong trust with the receiving
agent's normal capabilities, not a sandbox. When native integration is added,
peer text can also influence later owner turns. The preview does not isolate
authority secrets from another process running as your user.

Use an already installed, trusted preview binary. The invitation's built-in
`installed-preview/v1` profile hash identifies this preview's protocol policy;
it is **not** a signed publisher release manifest or permission to install a
binary obtained from an invitation page. Published installer qualification and
Internet/self-host acceptance remain separate work.

## Prepare each user

The two users need a reachable HTTPS relay with a valid certificate for its
configured authority. Follow [relay operations](operators/relay.md) for TLS,
storage, private probes and proxy configuration. Use one exact HTTPS origin,
without a path, query, fragment or trailing slash, for both clients:

```sh
peerturn init --file-permissions --relay https://relay.example --session preview-a
```

Run the same command as the joining user with `--session preview-b`. These are
owner-selected local labels; no cwd, process discovery or other agent session is
attached. `init` returns JSON including `state`, `binding: "test_session"`,
`session`, identity `fingerprint`, public `routing_key` and capabilities. An
existing identity is not silently replaced by another `init`.

File-permissions mode requires the explicit `--file-permissions` opt-in. Private
identity, session and routing keys live in the encrypted `client.sealed` journal.
The local wrapping key is the user-owned `0600` `seal.key`, outside the encrypted
SQLite records. This is filesystem custody, without an OS keychain or passphrase
protection against another process with the same uid. Keep the state directory
private (`0700`), retain `seal.key` with the state, and never replace a missing
key to make an old database open. See [M1b storage](store-m1b.md).

Public settings use `$XDG_CONFIG_HOME/peerturn/config.toml`, falling back to
`~/.config/peerturn/config.toml` on Linux or Application Support on macOS.
The `0600` TOML contains the selected state directory, relay, storage mode and
optional advertised-key consistency value. It contains no private keys, sessions
or invitation secrets. The legacy TOML name is `pinned_relay_key`.
An explicit `--state-dir` keeps its `config.toml` inside that state directory;
pass the same directory to `daemon start`. Malformed or unsafe configuration
fails closed; an existing different choice is not silently overwritten.

State defaults to `$XDG_STATE_HOME/peerturn` when set; otherwise it uses
`~/Library/Application Support/PeerTurn` on macOS or
`~/.local/state/peerturn` on Linux. An explicit `--state-dir` is supported by
`init` and `daemon start`; it must be a canonical absolute path with private
directories and no symlink components. On macOS, explicit temporary paths use
their canonical `/private/...` spelling.

The network client authenticates the relay through HTTPS/WebPKI, requires TLS 1.2
or later and does not follow redirects. `--relay-key PUBLIC_RELAY_KEY` adds an
optional consistency check against the unsigned discovery `relay_key`; the
library calls this `ExpectedRelayKey`. The value is retained locally and checked
once before operations on each client instance. This is not a cryptographic
relay-key pin: no signature or proof of private-key possession is verified, and
a substitute that can terminate valid TLS can echo the same public value. A
value copied from discovery is unsigned trust on first use (TOFU), without
authentication beyond WebPKI. The value never grants E2E peer or human trust.

## Authorize the inviter and start daemons

The relay operator must add the inviter's public `routing_key` from `init` to
the relay's `admin_keys`, then load that configuration. Copy only the public
value; client private keys stay on the client:

```toml
admin_keys = ["PUBLIC_ROUTING_KEY_FROM_INVITER_INIT"]
```

This is an operator-controlled relay administrator authorization. It permits
mailbox enrollment and encrypted invitation publication; it does not issue E2E
grants or authorize reading somebody else's mailbox. The second user needs no
admin entry: a winning invitation claim carries a voucher scoped to one joining
mailbox. Creating a new invitation from that second user would require its own
admin authorization.

Run a daemon in a terminal under each user's uid:

```sh
peerturn daemon start
```

The daemon stays in the foreground. Linux needs `XDG_RUNTIME_DIR`: `$XDG_RUNTIME_DIR/peerturn/<uid>/daemon.sock`.
macOS uses it when set, or a canonical uid-specific directory below private
`TMPDIR`; without either, daemon startup returns `runtime_unavailable`, never
falling back to shared `/tmp`. The final component is not symlink-resolved.
Runtime is independent of `--state-dir`. Clients use explicit `XDG_RUNTIME_DIR`,
then the private-state runtime pointer, then the platform default. MCP resolves
lazily until its first successful hello, then pins that directory; a changed
selection returns `needs_rebind` without contacting it. Late daemon startup can recover before hello; hostile pointers fail closed.

The runtime directory is `0700`, the Unix socket and lock file are `0600`, and
both sides check the connected peer uid. An advisory `flock` excludes another
daemon using that runtime location for the lifetime of shutdown as well as
normal operation. A stale socket is recovered only after the lock is acquired.
An additional `0600` `state.lock` inside the private state directory protects
the sealed journal for the entire lifetime of both daemon and initializer.
Different launchd/terminal runtime directories cannot open the same state twice.
Journal ownership, regular-file type, permissions and a single link are checked.
Local IPC has no TCP listener. Use separate OS users or machines for two normal
CLI daemons; the isolated runtime overrides in Go fixtures are not a CLI session
discovery mechanism.

## Invite, join and wait for the signed hello

From the inviter's second terminal:

```sh
umask 077
peerturn invite create --current --session preview-a --scope coauthor > invitation.json
```

The result is JSON with `url`, `expires_at`, `scope: "coauthor"` and
`binding: "test_session"`. `--current` still requires the explicit `--session`;
it does not detect the current terminal's native agent. The invitation is
single-use and lasts at most ten minutes. The daemon publishes its encrypted
descriptor using the admin-signed `POST /v1/invites/{id}` endpoint. This extends
M2's local bootstrap-file provisioning without changing the relay database
schema. Scopes, grants and session chains stay inside E2E ciphertext; the relay
receives the encrypted descriptor, public proof key, expiry and enrollment
voucher, retaining the voucher's hash.

The URL's capability secrets are in its `#fragment`. Normal HTTP fetches omit
that fragment, but a pasted URL can enter terminal scrollback, chat transcripts,
clipboard history or logs. Treat `invitation.json` and the complete URL as
secrets. Transfer only to the intended recipient through a trusted channel; do
not put the URL into command arguments, issue text or telemetry.

On the joining user's machine, pass the raw `url` value through stdin. For
example, with a private `0600` file containing only the URL:

```sh
peerturn join --link-stdin --session preview-b --scope coauthor < /secure/path/invitation-url.txt
```

There is no `--link URL` argument. The link must name the relay configured at
initialization; it cannot redirect the daemon to another relay. The client
validates the encrypted descriptor, profile hash, inviter chain, scopes and
public routing keys before creating its signed claim and independent return
grant. An invitation fingerprint authenticates the pinned cryptographic root;
human identity still requires your trusted exchange with that person.
Routing/session/identity collisions with an existing peer or local keys return
`conflict` before any peer or grant installation. Mailbox lookup uses a unique
index built from verified bindings. Expiry never releases an old route binding.

The initial result normally says `state: "waiting_inviter"`. This is retained
onboarding state, not completed peer access. Keep both daemons running: the
inviter verifies the claim, installs exact directional grants and routing
permits, and sends a signed encrypted hello; the joining side verifies it and
returns its hello. Inspect the result:

```sh
peerturn peers --session preview-a
peerturn peers --session preview-b
```

Proceed when the selected peer reports `connected`. The `id` from `peers` is
the value for `--peer`. A relay claim storage response alone is insufficient.
Lost responses retry the retained invitation/claim/hello ciphertext rather than
silently changing identity or consuming another invitation.

## Send and inspect explicit text

Inspection and messaging commands return JSON, with or without their accepted
`--json` flag. Normal peer/message/grant commands require the daemon's exact
`--session` label.
`status`, `doctor`, `daemon status` and `daemon stop` can run without one.

```sh
printf '%s\n' 'Please review this explicit message.' |
  peerturn send --session preview-a --peer PEER_ID --kind coauthor --stdin

peerturn inbox --session preview-b

printf '%s\n' 'Here is my explicit reply.' |
  peerturn reply --session preview-b --message MESSAGE_ID --stdin

peerturn receipt --session preview-a --message MESSAGE_ID
peerturn status
peerturn doctor
```

`receipt MESSAGE_ID --session preview-a` is also accepted. Bodies must be
nonempty UTF-8 and at most **16 KiB in bytes**. Only stdin text is sent. There
is no automatic file, history or transcript attachment, `@path` expansion,
URL-content fetching or token collection. Reading `inbox` returns local literal
`body_utf8`; it does not submit the text to a native agent. The list exposes
pending admitted data, excluding parked futures, controls, expired work and
already attempted work. Replies preserve the verified message's conversation,
parent, budget and hop binding.

Inbox JSON is `{ "messages": [...], "next_cursor": "..." }`. A page contains at
most 24 messages and fits a bounded IPC byte budget. When `next_cursor` is present,
continue with `inbox --session preview-b --after CURSOR`. Omitted messages remain
in custody; paging does not acknowledge native input or delete them. An expired
or missing cursor produces an empty page; restart without `--after` to inspect
the current retained inbox.

The three supported positive receipt stages are distinct:

| Stage | Evidence |
| --- | --- |
| `sender_stored` | The immutable outgoing encrypted packet committed locally. |
| `relay_stored` | The relay committed encrypted custody. |
| `receiver_stored` | The recipient committed authenticated local custody and its E2E receipt. |

None of these stages proves adapter acceptance, model input, turn completion or
reply. `status` reports `binding: "test_session"`, supported `coauthor` scope,
last successful sync time and sanitized last error. `doctor` checks relay discovery
and reports storage mode plus unavailable native adapters/guard; `e2e: true`
describes the encryption capability. The capability fields for attach, idle
wake, boundary delivery, fork responders and isolated authority secrets remain
false.

## Revoke a recipient-issued grant

```sh
peerturn grants list --session preview-b
peerturn grants revoke --session preview-b --grant GRANT_ID
```

`grants revoke GRANT_ID --session preview-b` is equivalent. The catalog includes
expired and revoked grants with exact issuer/subject bindings, scope, expiry and current epoch.
`revoked` is local policy; `effective_revoked` also includes authenticated outbound revocation receipts, including native reconciliation, and the persisted peer revocation state matched to that exact outgoing grant. The peer state preserves the displayed revocation after receipt garbage collection.
Select the direction issued by your local receiving session; you cannot revoke another recipient's E2E grant.

Revocation commits the local epoch/failure fence and quarantines affected
pending data before route cleanup is considered complete. Its result includes
`state: "revoked"` and `relay_pending`; a true value means relay permit removal
will retry after connectivity returns. Signed terminal receipts use a separate
control reserve. If the return grant has expired, local revoke still fences the
grant; `notifications_unavailable: true` reports that signed peer notifications
could not be sent under that expired authority. Revocation cannot undo text
already seen by a person or any
future agent effects already admitted under strong-trust coauthor authority.
The independent reverse grant is not silently revoked.
The preview also blocks new owner sends to a peer whose local incoming grant
was revoked, so `peers: revoked` means no new outgoing data to that peer. Signed
reverse-channel revocation receipts can mark outgoing authority revoked;
unsigned relay responses cannot. A missing or expired receipt return grant
causes a bounded terminal mailbox rejection, allowing other peers to progress.

## MCP proxy

For an explicit preview test session, configure an installed MCP host to launch:

```sh
peerturn mcp --session preview-a
```

For a native session, use the verified absolute installed executable with arguments `["mcp", "--current"]`. Claude resolves its existing native challenge.
Codex permits initialize and `tools/list` without a daemon capability, then binds
on the first `tools/call` using host-owned `params._meta.threadId`. The daemon
verifies that exact live native binding before issuing its session capability;
every later call must match. An inherited `CODEX_THREAD_ID` adds a matching
constraint, never startup authority. Missing/malformed proof returns
`binding_error`; conflicting proof returns `binding_mismatch`, both `needs_rebind`.
Only MCP protocol output goes to stdout; no UUID/token or shell wrapper is saved.

The host must supply proven binding and the same private runtime environment; tool-child
fixtures do **not qualify** fresh host MCP activation or live exchange.
`peerturn setup claude|codex` registers this stdio entry explicitly; plugin-only
installation does not. Follow the exact [MCP verification](onboarding.md#mcp-decision-and-verification)
in the selected session before using `peer_join`. Do not substitute another
session, save native tokens in configuration, or infer binding from shared cwd.
If the host cannot supply proven binding, use the owner's interactive
`join --current --link-stdin` terminal flow described in [installation](install.md).

The daemon must already be running under the same uid and selected private state/runtime profile.
The proxy speaks bounded JSON-RPC over stdio, binds to the selected session and exposes these tools:

| Tool | Required arguments |
| --- | --- |
| `peer_list` | None. |
| `peer_join` | None (`{}`); optional nonsecret `handle` selects a pending owner invitation. No text/URL argument. |
| `peer_send` | `peer`, `kind: "coauthor"`, `body`. |
| `peer_reply` | `message_id`, `body`. |
| `peer_inbox` | None. |
| `peer_receipt` | `message_id`. |
| `peer_status` | None. |

Owner decision, **23 October 2026**, supersedes `peer_join.text`: eligible owner hooks
extract/normalize the explicit paste using the CLI's strict parser and private same-UID IPC.
Claude binds it to the verified native epoch; Codex to the exact root thread matched by
host-owned `_meta.threadId`. A label-only proxy cannot join. Same-UID native host/hook IPC
is trusted, not independent human-origin authentication. Claude's classic hook records nothing;
its human-composer mod does. Codex excludes PeerTurn queue frames; internal Review shares root `session_id` without agent fields, so the daemon also proves root metadata and the hook's active `turn_id` with `rootTurnId == turn_id` via native `thread/turns/list` (`itemsView: notLoaded`) before recording invitations or offering/acknowledging inform. Review can forward child events into root history; membership alone is insufficient. Missing/inherited root IDs fail closed, including unqualified continuation chains. This has source/test evidence; live `/review` remains unqualified.
The daemon keeps ≤8 pending capabilities/session, memory-only for ≤10 minutes, cleared on
use, expiry, unbind/rebind, stop or restart; new distinct pastes evict the oldest and wipe its bytes/timer. Claude records owner pastes before waiting on operation serialization. No pending secret/prose is persisted, logged,
returned in status/receipts/audit or replayed from transcripts. Existing sealed onboarding
recovery state after join begins is separate; the owner paste remains in provider/native transcripts.

Call `peer_join({})`; it accepts no text/URL/fragment. With multiple entries,
`ambiguous_owner_invitation.invitations` and `peer_status.owner_invitations` show only
`{handle, relay_host, routing_hint, age_seconds}`; `routing_hint` is `/i/` plus six public ID characters, never fragment data. The owner's selection supplies optional `handle`, a random
opaque nonsecret selector. No inviter label before descriptor authentication. `no_owner_invitation`
or `owner_invitation_expired` requires a fresh paste after hook/binding readiness;
Hooks discard malformed candidates; direct CLI `malformed_invitation` asks for an unchanged paste.
The daemon still enforces the configured relay, descriptor signatures, exact
peer bindings and directional coauthor grants. `waiting_inviter` is not connected.
Invitation link recognition in delivered PeerTurn coauthor, inform and reply content is best-effort:
common scheme-less, case, percent-encoded and surrounding punctuation variants are normalized
before hashing their routing claims. Retained claims are denied even if later pasted by the owner.
Each peer has an LRU bucket of at most 128 hashes; a global 1024-entry cap also evicts oldest entries.
Buckets last until eviction or restart. Peer volume never closes unrelated owner joining.
Transformed or evicted copies may escape recognition; the required owner-hook handoff is the MCP
guarantee within the supported hook boundary. Same-uid CLI access remains unrestricted.

MCP can join an owner-pasted invitation and thereby create directional coauthor authority after
the checks above. It cannot create invitations, initialize the client, revoke grants or control
the daemon. Tool arguments cannot select another session. The proxy does not expose raw authority
keys. This limited tool list does not make same-uid CLI access a security boundary, and attaching
the proxy does not itself prove native activation, model input or a restricted peer turn.
The origin checks cover PeerTurn deliveries and supported owner hooks. They do not prove general
provenance of other integrations or constrain the unrestricted same-uid CLI available to a coauthor
turn. Peer text can still influence later owner turns; the skills require an explicit owner request.
Each proxy holds an authenticated IPC lease; EOF, process exit or a closed
connection releases its capability. Explicit release and expiry also reclaim
the bounded capability table without restarting the daemon. Idle leases have
a separate limit of 128, preserving 64 active request slots for owner commands.
Capabilities expire after 15 minutes without valid calls and at an absolute 24-hour limit.
The proxy renews once after the daemon's `unbound` refusal, which
precedes command effects; transport or ambiguous failures never trigger that
resubmission. Graceful release has its own five-second cleanup window.

## Recovery and limits

The sealed client journal retains identities, exact outgoing reservations and
onboarding state. A sequence reservation and its exact packet are saved before
enqueue; inbound processing first passes admission, then journals its receipt
inside the builder before the atomic custody commit. Retry recovers the exact
reservation instead of allocating a fresh sender sequence or performing side effects inside a receipt builder.

The M1b custody transaction commits ciphertext, replay evidence, local body,
routing decision and any required signed receipt before ACK. Transport-only
bootstrap/expiry records advance only the highest **contiguous** committed
mailbox frontier; they do not skip unknown predecessors or authorize message
dispatch. Control records have independent storage budgets. The sealed journal's
pending metadata orders each outgoing channel by sender sequence, including
receipts, so a large offline backlog cannot jump beyond the replay window. WSS notifications
contain only mailbox/high-sequence hints; reconnect/fetch starts from durable
custody and does not depend on receiving every notification.
Brief notification connections retain exponential reconnect backoff even if
they delivered an event; only a connection lasting at least 30 seconds resets it.
The daemon restarts a failed notification subscription with bounded backoff,
including after an unauthorized upgrade or malformed event. Polling continues
while notifications recover.
Failed syncs retry with exponential delays from one to thirty seconds; wake
hints cannot bypass that delay. A successful sync resets the delay. Healthy
pending onboarding polls every two seconds.

Network drops and a relay restart leave durable client state available for
recovery. Mutating HTTP retries use new request signatures/nonces with the
original encrypted packet and message ID. An ambiguous outcome is not proof of
loss. Do not repeat a user `send` command as an automatic retry: that is a new
submission. No exactly-once native effects are claimed.

Relay response codes describe transport custody, not signed peer authority.
HTTP 410 `expired_message` means a new submit reached the relay after its expiry;
HTTP 403 `forbidden` means the relay denied that route. Neither permanently
revokes an E2E grant or blocks the channel from a later transport retry.

If a never-relayed outgoing packet expires, its reserved sender sequence cannot
be safely skipped. The affected peer becomes `needs_rebind`; new sends fail with
binding exit code 3 until new explicit binding/onboarding. A retry must not
manufacture a gap-skipping sequence. No native
rebind command or automatic continuity repair is supplied by this preview.
Key loss, stale certificates, storage backpressure and backup rollback likewise
do not grant permission to replace identity or reopen an earlier epoch.

Use `status`, `doctor`, `peers`, `receipt` and `grants list` to distinguish local
custody, connectivity, handshake, expiry and revoked authority. Public failures
are sanitized JSON with `code`, `message`, `retryable` and `state`; CLI exit codes
are 2 for rejected input/policy, 3 for binding failures, 4 for temporary
unavailability, 5 for authentication/key failures, 6 for unsupported capabilities
and 7 for an explicitly ambiguous native outcome. M2.5 never asserts a native
outcome merely from a storage response.

Stop the foreground daemon with Ctrl-C/SIGTERM or from another local terminal:

```sh
peerturn daemon stop
```

It responds `stopping`; the foreground process drains local workers and exits
with `stopped`. Restart with the same private state and runtime environment.
Keep [M1a](core-m1a.md), [M1b](store-m1b.md) and
[relay operations](operators/relay.md) as the detailed protocol/storage references.
