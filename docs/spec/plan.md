# Implementation and evidence plan v1

2026-10-21, owner's decision after M0/M0b. At the time, the product was a Go help/version CLI skeleton; protocol/adapters/responders were a design contract. M0/M0b below are completed labs, not completed product milestones. Requirements: [requirements.md](requirements.md); architecture: [design.md](design.md); restrictions: [security.md](security.md). The [Russian original](ru/plan.md) preserves the historical text.

Publication note: private paths are replaced by stable archive identifiers; original line references are retained. See the [historical citation key](../README.md#historical-citations).

## 1. Workflow and definition of done

Every vertical feature starts with reproducible failing acceptance scenario/fixture, then minimal implementation, negative cases, refactor. Harness has positive controls for read/answer and prohibited effect without restrictions; absent canary without attempted effect or proven tool removal does not verify enforcement. Passing unit simulation never replaces live runtime test.

All tests/lint/build use the Makefile; live fixtures/services stay local in isolated lab. Never execute researched third-party repositories: archived source snapshots are read-only as required by `BRIEF:16`. Private local bridge allowed as trusted reference, destructive canaries only in fixture filesystem. Auth/keys through separate test secret mounts, never recorded in results. Docker image/toolchain/runtime/source SHA pinned in every run manifest.

Source/test/doc files≤400 lines, split by responsibility/scenario; one assigned owner per file. Implement SQL schema/migrations only after explicit owner authorization. PR gets one independent finished-diff review for security, crypto, migrations, CI/release; critical findings block. Implementer runs targeted checks, integrator runs full required gate once; successful checks not repeated without new changes.

Evidence bundle per `LAB-*`: `scenario.yaml` with version/provider/OS/auth class, steps, expected result; `raw/` sanitized events/NDJSON and exit codes; monotonic timestamps; `result.json` assertions; short README with `path:line`, negative controls, limitations. Secrets, private-message bodies, access tokens redacted before publication. Evidence immutable between runs; new run gets new ID. Console exit 0 without model-input/turn evidence is not delivery.

Baseline topology: containers A(Claude), B(Codex), R(relay), X(untrusted peer/fault proxy), separate volumes and session keys; fixture workspace with allowed/prohibited canaries. macOS/claude.ai and OS keychain tests use separate host profile with same machine-readable result format, since Linux container does not prove host behavior. Gemini/agy/Copilot use separate pinned images or honestly labeled host run if runtime cannot be containerized.

Evidence hierarchy: pinned live M0/M0b/L1/L2/host Monitor → source/docs → new assumptions. DeepSeek success does not prove claude.ai or vice versa. Unpassed scenario is `unverified`/`unsupported`, never documentation-based `pass`. FR/NFR from requirements; every `LAB-*` used there is defined below.

## 6. Work that can run in parallel

After completed M0/M0b and typed scope/responder IPC freeze: one implementer owns `internal/adapters/claude` + `adapters/claude`, another Codex equivalents; each supplies own live evidence and targeted checks. Core protocol/responder supervisor/store has separate owner; adapters never copy its crypto/policy. After schema freeze, relay/API may separate from CLI/status; resolve API conflicts through contract fixtures before code changes.

Split boundary adapters by platform after join core is ready; supply-chain/install packaging and operator docs after stable signed manifest. Red-team scenario author may work independently using public wire/IPC contracts; reviewer never “confirms” results without raw evidence. Shared `go.mod`, schemas, generated manifests, integration harness have one integrator. Use scripts for bulk version/name/reference checks before multiple agents.

Critical path: completed M0b → M1 authority/responder IPC + M2 custody → M3/M4 qualified responders/inform/live adapters → M6 attacks/cost → M7 release. M0 stock guard/API is outside v1 critical path.

## 7. Risks and actions

| Risk | Early signal | Action / refusal criterion |
|---|---|---|
| Runtime profile not applied / tool integration bypasses boundary | Effective tool inventory/sandbox mismatch, MCP side effect | Ask unavailable, typed receipt, no live/unsandboxed fallback; qualified build/profile mandatory |
| Linux userns/AppArmor/seccomp / macOS Seatbelt unavailable | Sandbox preflight rejected | sandbox_unavailable/fork_responder=false, local remediation by environment owner; never weaken host policy automatically |
| Path read/exfil/inherited secret | Codex RO reads signer/admission credentials, Claude deny unmatched | Both runtimes must isolate authority keys/state/IPC before spawn or ask unavailable; broader read exposure separate. Redaction never replaces gate or DLP; history stays full |
| Stale/torn snapshot or model/effort drift | Prefix/model metadata unknown/mismatch | Wait native boundary or snapshot_unavailable/model_mismatch; no summary/cheap replacement or owner-turn restriction |
| Over-refusal / prompt injection | Benign grant-aware question refused or text impersonates owner | Fixed verified grant framing + benign/hostile controls; never weaken runtime security for cooperativeness |
| Cost flood/full context/cache miss | Reservation/usage unavailable, concurrent asks/overshoot | Receiver caps/queue/deadline, budget_unavailable or budget_exceeded; show estimates/residual billing, never silently lower quality |
| Duplicate execution/charge after crash | Submit/spawn/reply outcome unknown | in_doubt/reconciliation, no blind retry/fallback; owner retry with new ID and warning |
| Activation/compatibility/private protocols | Manual trust/reload, schema/profile hash mismatch | Truthful steps and same live UUID; new fork permitted for responder, not substitute attach; unknown version unverified |
| Invite bootstrap / static HPKE | Key only from unknown page; FS/PCS required | Trusted publisher/first-use card/TTL; MLS or other standard messaging stack separately, no custom ratchet |
