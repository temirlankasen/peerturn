21.10.2026, решение владельца после M0/M0b. Продукт — Go help/version CLI skeleton; protocol/adapters/responders пока проектный контракт. M0/M0b ниже — завершённые lab, не готовые product milestones. Примечание к публикации: частные пути заменены стабильными архивными обозначениями; исходные номера строк сохранены. См. [ключ исторических ссылок](../../README.md#historical-citations) и [английский перевод](../plan.md).

## 1. Порядок работы и определение готовности

Каждая вертикальная функция начинается с воспроизводимого failing acceptance scenario/fixture, затем минимальная реализация, затем негативные случаи и refactor. Harness имеет positive controls для чтения/ответа и запрещённого effect без restrictions; отсутствие canary без попытки effect или доказанного tool removal не считается проверкой enforcement. Успешная unit simulation не заменяет live runtime test.

Все tests/lint/build запускаются через Makefile; live fixtures/services остаются локально в изолированном lab. Нельзя исполнять исследованные чужие repositories: архивные снимки исходников — только для чтения, как требует `BRIEF:16`. Частный локальный bridge разрешён как доверенный reference, но его destructive canaries выполняются только в fixture filesystem. Auth/keys поступают через отдельные test secret mounts, без записи в results. Docker image/toolchain/runtime/source SHA закреплены в каждом run manifest.

Файлы source/test/doc≤400 строк, разбиение по ответственности и scenario; один назначенный владелец на файл. Реализацию SQL schema/migrations начинать только после явного разрешения владельца. PR имеет один независимый review готового diff для security, crypto, migrations, CI/release; блокируют критичные находки. Исполнитель делает targeted checks, интегратор один раз запускает полный обязательный gate; без новых изменений успешные проверки не повторяет.

Evidence bundle для каждого `LAB-*`: `scenario.yaml` с version/provider/OS/auth class, steps и expected result; `raw/` sanitized events/NDJSON и exit codes; monotonic timestamps; `result.json` с assertions; короткий README с `path:line`, negative controls и ограничениями. Secrets, body личных сообщений и access tokens редактируются до публикации. Доказательства неизменяемы между runs, новый run имеет новый ID. Console exit0 без model-input/turn evidence не считается доставкой.

Базовая топология: containers A(Claude), B(Codex), R(relay), X(untrusted peer/fault proxy), отдельные volumes и session keys; fixture workspace с разрешёнными и запрещёнными canaries. macOS/claude.ai и OS keychain tests — отдельный host profile с тем же machine-readable result format, поскольку Linux container не доказывает host поведение. Gemini/agy/Copilot подключаются отдельными pinned images или честно отмеченным host run, если runtime не контейнеризуется.

Иерархия оснований: pinned live M0/M0b/L1/L2/host Monitor → source/docs → новые предположения. Положительный результат на DeepSeek не доказывает claude.ai и наоборот. Непройденный scenario имеет `unverified`/`unsupported`, никогда `pass` по документации. FR/NFR — из requirements; каждый используемый там `LAB-*` определён ниже.

## 6. Что можно выполнять параллельно

После завершённых M0/M0b и freeze typed scope/responder IPC: один исполнитель владеет `internal/adapters/claude` + `adapters/claude`, второй — Codex equivalents; каждый приносит собственные live evidence и targeted checks. Core protocol/responder supervisor/store — отдельный владелец, adapters не копируют его crypto или policy. Relay/API после schema freeze можно отделить от CLI/status; конфликты API решаются контрактными fixtures до изменения кода.

Boundary adapters делятся по платформам после готового join core; supply-chain/install packaging и operator docs — после стабильного signed manifest. Red-team scenario автор может работать независимо от реализации, используя публичные wire/IPC contracts; reviewer не «подтверждает» результаты без raw evidence. Shared files `go.mod`, schemas, generated manifests и integration harness имеют одного интегратора. Массовые version/name/ref checks сначала скриптом, не множеством агентов.

Критический путь: завершённый M0b → M1 authority/responder IPC + M2 custody → M3/M4 qualified responders/inform/live adapters → M6 attacks/cost → M7 release. M0 stock guard/API не находится на v1 critical path.

## 8. Зафиксированные решения и дальнейшая квалификация

Утверждены PeerTurn/`peerturn`, Apache-2.0, ранний coauthor-only preview и новая scope routing модель от 21.10. In-session guard/upstream API M0 §Q6 — v2 option; внешние публикации proposal требуют отдельного явного разрешения. Исторические research/spec assumptions не выдаются за исходные owner decisions.

Открыты engineering evidence, а не повторное утверждение решения: hardened Claude tool/path profile, Codex read exposure/containment и network/MCP isolation, Seatbelt live, model/effort/snapshot continuity, budget accounting и полезное grant framing. До evidence соответствующий профиль unverified; полный v1 больше не ждёт stock in-session guard.

Grant24h/max30d, invite10min, ciphertext TTL24h/max7d, audit30d и per-ask limits — настраиваемые product defaults. Ask↔ask default доступен только при qualified fork на каждой receiving стороне; preview не выдаёт disabled scopes. Новые responder schema/migrations не реализуются без явного owner approval. Никаких registrations/publications/deploy в этом дизайне.
